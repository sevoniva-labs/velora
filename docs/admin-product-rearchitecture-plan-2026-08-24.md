# Velora 管理后台产品复盘与重构实施方案

状态：Phase 0–4 已实现并部署，自动门禁与认证管理 API 已验收；等待登录后的浏览器目视验收（2026-08-24）
日期：2026-08-24  
适用范围：Velora 管理后台、管理 API、Velora 与 Casdoor 管理边界  
技术约束：前端使用 `@ant-design/pro-components`；不修改 Casdoor；不建设 Velora 自有 OIDC Provider

## 1. 结论

当前后台不是“样式需要微调”，而是产品模型、信息架构、授权模型和操作流程同时存在结构性问题。技术接入链路虽然已经可以工作，但管理端仍是按数据库表、接口和工程步骤拼装的 CRUD 集合，普通管理员无法形成稳定心智模型。

当前版本不能定义为产品级管理后台。必须停止继续修补原有五步向导，改为以下产品主线：

```text
组织与人员
  → 平台角色
  → 应用
  → 应用角色
  → 访问范围
  → 有效权限
  → 账号下发
  → 验证与发布
  → 审计与复核
```

应用是后台的核心业务对象。应用资料、登录接入、应用角色、访问范围、账号同步、验证发布和变更记录必须全部收进同一个应用详情页。

## 3. 根本原因

### 3.1 按技术模块组织，而不是按管理员任务组织

当前一个应用被拆成：

- “应用管理”：基础资料；
- “访问策略”：谁能看到；
- “账号与访问”：单用户应用角色；
- “身份与单点登录”：OIDC、角色目录、账号下发、验证和发布。

管理员必须自己记住四个入口之间的关系。这是“看不懂、不会用”的直接原因。

### 3.2 两套授权模型互不联动

当前 `portal_access_policies` 只决定门户可见和启动，`user_application_entitlements` 单独决定下游账号和应用角色。两者没有统一来源，因此会出现：

- 用户能看到应用，但没有下发账号或角色；
- 用户已下发账号，却看不到应用；
- 部门、用户组、平台角色变化后不会自动重算应用权限；
- 系统无法解释某项权限来自部门、组、角色还是直接授权。

### 3.3 把一次性接入流程当成永久管理页面

已发布应用仍展示五步向导。向导同时承担状态、角色、同步、密钥、审批、验证和发布，造成页面过长、操作层级混乱。发布后应进入运行管理模式，不应继续显示 onboarding wizard。

### 3.4 内部实现细节直接暴露给用户

页面直接显示 `PUBLISHED`、`RECONCILE_PROVIDER`、`SUCCEEDED`、`LOCAL`、`system_admin`、UUID、Issuer 和技术检查名。管理员不应该理解这些内部枚举。

### 3.5 ProComponents 已安装但没有成为页面骨架

项目已安装 `@ant-design/pro-components`，当前后台仍主要由原生 `Card + Form + Table + Modal + Alert` 手工拼装。问题不是“没有组件库”，而是没有使用：

- `ProLayout` 统一后台骨架；
- `PageContainer`/统一 PageHeader 管理对象上下文和主操作；
- `ProTable` 管理查询、列、工具栏、批量操作和服务端分页；
- `EditableProTable` 管理应用角色目录；
- `ProDescriptions` 管理应用和用户详情；
- `ProForm`/`DrawerForm`/`ModalForm` 管理编辑；
- `QueryFilter` 管理复杂筛选；
- `StepsForm` 只用于真正的一次性创建流程。

### 3.6 缺少页面级产品规则

当前没有约束每页为什么存在、谁使用、主操作是什么、什么信息应该常驻、什么内容应该渐进展示，导致大段 Alert、说明文案和多个同级按钮堆叠。

## 4. 已确认的 P0 产品缺陷

### P0-1：访问策略文案与真实行为相反

访问策略页写“暂无规则，所有登录用户可见”，后端真实行为是“无规则默认拒绝”。管理员按照错误提示操作会让所有用户失去访问权限。

### P0-2：应用表单存在不会保存的假字段

页面收集“关键词、负责人、所属部门”，但请求没有发送这些字段，后端契约也没有对应字段。管理员填写后数据实际丢失；页面还会把 `createdBy` 冒充成负责人。

### P0-3：生命周期与启停状态混淆

OIDC 应用的“接入中”被列表显示成“停用”。`DRAFT / WAITING / READY / PUBLISHED` 是接入生命周期，`ENABLED / DISABLED` 是运行状态，不能混为一个状态列。

### P0-4：生产应用提供列表一级硬删除

应用列表直接显示“删除”，并声称策略、收藏和访问记录会一并删除。生产产品应先停用、归档、保留审计，再由数据保留策略异步清理。

### P0-5：高风险操作和普通保存混在一起

“保存账号与权限配置”“配置访问范围”“轮换同步密钥”并排；验证页“运行检查”“提交发布”“发布应用”同时出现。管理员无法判断当前唯一正确动作。

### P0-6：角色保存可能部分成功

角色目录与账号同步配置由前端顺序调用不同接口。前一步成功、后一步失败时会形成部分成功，但页面把它表现为一次保存。

### P0-7：管理员 MFA 可能形成操作死路

部分高风险管理操作要求近期 MFA，但生产模式下 Velora 本地 MFA 已关闭，Casdoor MFA 又没有完整映射为 Velora 内的自助和 step-up 流程。必须先补统一身份的 MFA 状态和 step-up 闭环。

## 5. Velora、Casdoor 和目标应用的最终边界

| 能力 | 事实来源 | 日常管理入口 |
|---|---|---|
| 用户资料、账号状态 | Velora | Velora |
| 组织、部门、岗位、用户组 | Velora | Velora |
| 平台角色、后台权限、数据范围 | Velora | Velora |
| 应用目录、负责人、分类、生命周期 | Velora | Velora |
| 应用角色、访问范围、有效权限 | Velora | Velora |
| 账号下发、重试、对账、审计 | Velora | Velora |
| 密码凭证、MFA 因子、Passkey | Casdoor | Velora 提供产品入口，Casdoor 执行 |
| OIDC Client、Token、认证会话 | Casdoor | Velora 自动编排 |
| 应用内业务鉴权和数据权限 | 目标应用 | 目标应用 |
| Casdoor 控制台 | Casdoor | 仅 break-glass，应急使用 |

边界原则：

1. 管理员标准工作流打开 Casdoor 的次数必须为 0。
2. Casdoor 账号是认证执行副本，不能与 Velora 双向人工维护。
3. Casdoor 管理入口不进入普通导航、应用向导或页头。
4. 应急入口放在“平台设置 → 身份引擎 → 应急操作”，默认关闭。
5. 应急入口要求专门权限、近期 MFA、填写原因、二次确认和完整审计。
6. Casdoor 不可用时，Velora 显示“等待同步/同步失败”，不能伪成功。

## 6. 核心概念必须重新定义

### 平台角色

控制用户在 Velora 后台能做什么，例如系统管理员、应用管理员、身份管理员、审计员。

### 应用角色

控制用户进入某个业务应用后拥有什么业务身份，例如 Spectra 的开发人员、审计员、项目管理员。

### 访问范围

把部门、用户组、平台角色或指定人员映射到“应用 + 应用角色”。

### 有效权限

系统根据组织关系和访问规则计算出的最终结果，是门户可见、OIDC 授权和账号下发的唯一依据。

### 直接人员授权

只作为例外路径，必须显示来源、有效期和变更原因，不能成为主要授权方式。

```text
工作台
├── 待处理事项
├── 风险与异常
└── 最近变更

应用中心
├── 应用
│   └── 应用详情
│       ├── 概览
│       ├── 应用信息
│       ├── 登录配置
│       ├── 角色与访问
│       ├── 账号同步
│       ├── 验证与发布
│       └── 变更记录
└── 分类与标签

组织与人员
├── 用户
├── 部门与岗位
└── 用户组

权限治理
├── 平台角色
├── 临时授权
└── 访问复核

安全与审计
├── 登录安全与 MFA
├── 在线会话
├── 服务账号
└── 操作审计

平台设置
├── 门户展示设置
├── 配置发布与回滚
└── 身份引擎诊断（隐藏/break-glass）
```

必须从顶层菜单移除：

- 分类管理；
- 标签管理；
- 访问策略；
- 身份与单点登录。

它们不是独立业务任务，不能和“应用”“用户”并列。

## 8. 应用详情是唯一应用管理入口

### 应用列表

只展示：应用、接入方式、生命周期、有效访问人数、同步健康、负责人、下一项待办。点击应用名称或“管理”进入详情。

行内不再显示“接入配置、编辑、删除”三个同级动作。停用、归档放入更多菜单，物理删除不向普通管理员开放。

组件：`ProTable`，服务端分页和筛选；页面只保留一个主按钮“新建应用”。

### 应用概览

展示：当前状态、下一步、有效访问人数、账号同步健康、最近发布、最近异常和待处理事项。技术枚举转换成中文业务状态。

组件：`PageContainer + ProCard + StatisticCard + ProList`。

### 应用信息

负责人和所属部门使用真实对象选择器，不能输入自由文本。应用编码创建后不可变。状态和生命周期分开展示。

组件：`ProDescriptions` 查看，`DrawerForm` 编辑。

### 登录配置

正常管理员只看：是否启用统一登录、回调地址、配置领取状态、最近检测结果。Issuer、Scopes、Client ID 放入“高级信息”，Provider Ref 不向业务管理员展示。

组件：`ProDescriptions + DrawerForm`。

### 角色与访问

应用角色使用 `EditableProTable`，每行一个角色，不再一张角色一张 Card。访问范围放在同一 Tab 的下半部分，保证管理员在一个应用上下文内完成授权。

### 账号同步

展示 Endpoint、最近成功、失败原因、密钥版本和重试状态。密钥轮换进入独立危险操作区，不能与普通保存并列。

### 验证与发布

检查项使用中文名称、结果、失败原因和修复动作。不同状态只显示一个主要按钮。提交审批后由系统自动继续，不要求管理员反复点击同一动作。

### 变更记录

展示谁在何时修改了什么、影响多少人、审批记录、当前版本和可回滚版本。

## 9. 应用访问范围的产品模型

管理员配置的应是：

```text
哪些人 → 可以访问哪个应用 → 获得哪些应用角色
```

支持的主体：

- 全体成员；
- 部门，可选是否包含子部门；
- 用户组；
- 平台角色；
- 指定人员；
- 排除人员；
- 生效与失效时间。

访问规则表：

| 访问对象 | 覆盖人数 | 应用角色 | 有效期 | 状态 | 来源 |
|---|---:|---|---|---|---|
| 研发中心及子部门 | 86 | 开发人员 | 长期 | 生效中 | 部门 |
| 安全审计组 | 7 | 审计员 | 长期 | 生效中 | 用户组 |
| Carson | 1 | 项目管理员 | 2026-09-30 | 待审批 | 直接授权 |

保存前必须预览：新增人数、撤销人数、角色变化人数、高权限人数和预计下发任务数。

确定性规则：

1. 应用停用或用户停用，直接拒绝；
2. 显式人员排除优先；
3. 匹配的允许规则取应用角色并集；
4. 无匹配默认拒绝；
5. 没有业务角色的应用可使用“仅访问”；
6. 门户可见、OIDC 授权和账号下发读取同一个有效权限结果。

## 10. 后端模型与 API 改造

后端约 60%–70% 的组织、RBAC、审批、审计、Casdoor 和 Provisioning 基座可以复用。重点新增统一授权模型。

### 新增数据模型

`application_access_grants`：

- organization_id、application_id；
- subject_type：EVERYONE、DEPARTMENT、USER_GROUP、PLATFORM_ROLE、USER；
- subject_id、include_descendants；
- effect：第一版 ALLOW/EXCLUDE；
- valid_from、valid_until、status、reason、version；
- created_by、updated_by、approval_id。

`application_access_grant_roles`：授权规则与应用角色的关联。

`user_application_entitlement_sources`：记录最终权限来自哪些规则，用于解释、复核和撤权。

现有 `user_application_entitlements` 保留，但改为计算结果和账号下发投影，不再作为主要人工配置入口。

### 关键 API

- 应用聚合详情；
- 应用访问规则 CRUD；
- 访问变更影响预览；
- 有效访问用户与权限来源查询；
- 账号下发状态与失败重试；
- 用户分页、搜索、筛选和详情；
- 平台角色创建、编辑、复制、停用；
- 部门树、岗位、用户组的聚合查询；
- Velora 内的 MFA 状态、step-up 和会话撤销。

## 11. ProComponents 页面规范

| 场景 | 必须使用 | 禁止继续使用 |
|---|---|---|
| 全局后台 | `ProLayout` | 自定义蓝色渐变顶栏和玻璃侧栏 |
| 页面容器 | `PageContainer` 或统一 PageHeader | 每页手写 h2、p 和大段 Alert |
| 查询列表 | `ProTable` | 手拼 Input.Search + Table + 前端分页 |
| 复杂筛选 | `QueryFilter` | 多个自由拼接 Select/Input |
| 应用角色 | `EditableProTable` | 一个角色一张 Card 的超长表单 |
| 对象详情 | `ProDescriptions` | 多套散落 Descriptions/Card |
| 编辑对象 | `DrawerForm`/`ModalForm` | 无固定 footer 的超长 Modal |
| 配置页 | `ProForm` | 大段内联 JSX 表单 |
| 一次性创建流程 | `StepsForm` | 手写 Steps + 多组 Alert/Card |

视觉基线：

- 页面背景 `#f7f8fa`；
- 白色业务卡，8px 圆角，轻投影；
- 内容区统一 24px；页面区块间距 16px；
- 移除后台玻璃渐变、光晕、过度阴影和大圆角；
- 一级页面默认不显示面包屑；详情页才显示；
- 页面标题下默认不放说明 Alert；只有非显而易见的风险规则才允许单行、可关闭提示；
- 每页一个主要按钮；危险操作进入更多菜单或危险操作区；
- 业务状态必须中文化，内部编码只出现在高级信息或诊断抽屉。

## 13. 文案与按钮规则

1. 删除解释实现架构的大段文案。
2. 页面标题只说明当前任务，不写宣传语。
3. 字段提示贴近字段，复杂规则进入帮助抽屉。
4. “下一步”改为明确动作，如“继续配置访问范围”。
5. “申请审批并生成接入配置”改为“提交接入申请”。
6. “提交发布”和“发布应用”不得同时出现给同一角色。
7. “删除应用”改为“归档应用”。
8. 不显示内部枚举、UUID、技术操作码。
9. 无权限、无应用、无数据都是合法空状态，不显示网络错误。
10. 加载使用骨架屏或局部加载，不允许整页空白转圈。

## 15. 数据迁移

1. 数据库只做 additive migration，不删除旧表。
2. 现有直接 entitlement 迁为 USER 类型直接授权规则。
3. 现有 EVERYONE/ORGANIZATION/ROLE/GROUP 策略迁为访问范围规则。
4. 旧策略没有应用角色时不得静默猜测；多角色应用必须管理员确认默认角色。
5. 新授权引擎先 shadow 计算，对比新旧有效用户集合。
6. 对账一致后按应用切换门户访问、OIDC 授权和账号下发读取路径。
7. 旧表在稳定期内只读保留。

## 16. 验收标准

以下主链路必须由一个正常管理员只在 Velora 内完成：

```text
创建部门和用户
→ 配置平台角色
→ 创建应用
→ 配置应用角色
→ 按部门/组/平台角色/人员开放应用
→ 预览最终人员和权限来源
→ 下发账号
→ 验证并发布
→ 查看审计并执行回滚
```

硬性门槛：

- 标准管理流程 Casdoor 点击次数为 0；
- 顶层没有分类、标签、访问策略、身份向导等割裂菜单；
- 一个应用的全部管理都在应用详情完成；
- 不要求管理员输入任何原始 ID；
- 已发布应用不再显示接入向导；
- 用户详情能解释每项应用权限的来源；
- 部门调动、组变更、角色变化和账号停用会自动重算并撤权；
- 后台不出现内部英文状态和冗长技术说明；
- 页面使用 ProComponents 标准模式，不再手拼重复 Card/Form/Table；
- 所有关键流程有单元测试、组件测试和生产真实验证。

## 17. 回滚方案

- Web 可回滚旧构建；Server 保持旧 API 和旧表读取兼容；
- 授权引擎回滚时切回旧读取路径，新表数据保留；
- 发布前导出应用、策略、entitlement、组织关系和有效人数基线；
- 回滚不删除 Casdoor 用户、Client 或已签发密钥；密钥问题只能轮换；
- 每个 Phase 独立 Conventional Commit，提交后立即推送 `main`，保证可逐阶段回退。

## 18. 最终判断

后端底座可复用，不需要推翻重写。真正必须重做的是管理端产品层，以及“访问范围 → 有效权限 → 账号下发”这一条统一授权链路。

在本方案 Phase 0–4 完成前，不应再宣称 Velora 管理后台已达到产品级。继续修补当前向导只会增加认知负担和维护成本。
