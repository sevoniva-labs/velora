# 中国企业 / 金融行业安全与合规工程基线

> 本文用于脚手架设计映射，不构成等保、密评、数据合规或金融监管合规结论。最终要求以组织制度、系统定级、数据级别、部署边界和测评结果为准。

## 1. 参考基线

Forge 在应用工程层重点参考以下现行/常用规范体系：

- GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》
- GB/T 39786-2021《信息安全技术 信息系统密码应用基本要求》
- 《中华人民共和国网络安全法》及 2026-01-01 起施行的修订决定
- 《网络数据安全管理条例》
- JR/T 0071.1—2020、JR/T 0071.2—2020 金融行业网络安全等级保护实施指引
- JR/T 0197—2020《金融数据安全 数据安全分级指南》
- JR/T 0223—2021《金融数据安全 数据生命周期安全规范》
- JR/T 0171—2020《个人金融信息保护技术规范》
- JR/T 0256—2022《金融行业信息系统商用密码应用 测评要求》

标准编号、适用范围和组织最新制度应在项目立项/架构评审时再次核验。

## 3. 日志与留存

`financial` / `mlps3` profile 将 `network_log_retention_days` 的配置下限设为 183 天，防止项目配置成明显低于网络日志六个月要求的值。

注意：应用本身不会通过一个数据库表承担所有网络安全日志的长期留存。生产应将 stdout/审计日志集中到日志平台/SIEM，并根据制度配置在线、近线、归档和防篡改策略。高敏审计可扩展 WORM/对象锁定或独立审计库。

## 4. 金融数据

脚手架只提供“字段脱敏工具”和安全边界，**数据分类分级必须由具体业务定义**。推荐每个项目维护：

- 数据目录与数据分类分级
- 字段敏感级别和展示/导出规则
- 生产数据使用审批和脱敏规则
- 数据最小化、保存期限和删除规则
- 跨境/对外共享/第三方处理边界（如适用）
- 数据库备份、日志备份、密钥备份与恢复控制

业务 Repository/DTO 不应直接依赖统一“自动脱敏”猜测，应在明确的数据策略下应用 masking/authorization。

## 5. 商用密码

Forge 的 `gm` Provider 当前是应用层 SM3 + SM4-GCM 能力基线，不等同于完整商用密码应用方案。银行生产通常还需结合：TLS 国密套件、数字证书、签名验签、SM2、密钥生命周期、密码机/HSM/KMS、双人双控、密钥备份恢复和密评要求。

因此 HSM/KMS/密码机放在 `integrations/secrets/hsm` 扩展位，项目只有在目标密码产品和部署环境验证完成后才能在兼容矩阵标记“已验证”。

## 6. 三员分立与最小权限

默认角色：

- `system_admin`：系统配置和用户管理，不应自动拥有审计归档删除能力
- `security_admin`：安全策略和安全运营权限
- `auditor`：审计查看/导出，默认不具备用户创建和业务写权限

角色按组织隔离，Permission 标识作为代码/API 契约全局定义。具体银行如采用更细的岗位分离，应通过 Permission 扩展，不在业务代码里写死角色判断。

## 7. 生产上线必须补齐

框架不能替代：WAF、API 网关、主机/容器/DB/中间件加固、堡垒机、网络分区、备份容灾、密评、等级保护测评、应急预案、账号治理、日志平台、SIEM/SOC、病毒/恶意文件检测、数据防泄漏、运维制度和人员控制。
